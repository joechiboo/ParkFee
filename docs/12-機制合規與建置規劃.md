## 1. 核心流程與範圍

聚焦三步核心閉環，其餘下游延後：

1. **登記（含預選位）** — 住戶填 戶號/車號/車種/第幾輛/身障/志願小位/電話 ＋ 預選位（志願）。
2. **電腦抽籤** — 固定種子抽「順序」，依順序統一分發志願；可重現、可監察。
3. **結果** — 誰分到哪個位、應繳、簽約期限、候補序；可匯出、可套印合約（附件一）。

**延後（定案後才用到）**：eTag 白名單匯出、巡邏稽核、車牌辨識、繳費狀態追蹤、退費試算、勸導單（附件四）。

### 1.1 實際規模（依現有 eTag 名冊，2026-06 取得）

| 項目 | 數量 | 來源/備註 |
|---|---|---|
| 機車（現有登記）| **475 台**（462 不重複）| eTag 名冊「機車車牌」非空 |
| 汽車 | 925 台（903 不重複）| 參考，本專案不處理汽車承租 |
| 戶數 | 約 625 戶 | eTag 名冊「戶別」相異 |
| 機車位（供給）| 655 | B1 平面圖（大320/小327/無障礙8）|

**關鍵推論**：
- **機車供 655 > 求 475 → 第一輪幾乎人人有位、抽籤壓力小**（除非大量第 2/3 台把需求推高）。
- 475 筆登記量不小 → 登記策略採「**預填/確認**」：住戶輸戶號帶出名下既有車，確認即可，避免逐筆打字。
- eTag 名冊**含戶別↔車牌對應** → 可作為「戶號+車號」認證的比對底稿與預填來源；但有重複車牌、歷史註記（社宅/租客/新屋主）、續列空戶別等需清洗，故仍以**登記活動重建乾淨對應、臨櫃查行照為準**。
- 名冊為個資，存於 gitignored `private/`，不進 repo。

## 3. 車位類型與重機模型

**車位物理類型只有三種**：大（320）、小（327）、無障礙（8）。

**重機不是第 4 種車位**：250CC↑紅黃牌重機本身無專屬車位，肆五規定「機車位足額時停放於**雙機車位**」＝佔用**兩個相鄰的「大」位**。肆四另允許重機停汽車位（本專案不處理汽車位）。

**住戶選位的選單**：

| 住戶選 | 對應實際車位 |
|---|---|
| 小位 | 1 個「小」 |
| 一般 | 1 個「大」 |
| 重機 | 2 個相鄰「大」（雙位）|
| （無障礙）| 身障專屬優先軌，不在一般選單 |

**選位/地圖待補的資料（卡住預選位）**：
1. **大／小／無障礙分型**：655 個機車位目前為單一序列 1..655，尚未分型。已知 20 個型別（來自公益編號清單），其餘需依平面圖車格寬窄判定。
2. **重機雙位配對**：標記哪兩個相鄰大位可組成一組雙位。

> 註：引擎已具備重機邏輯（取 2 大位），缺的是「地圖/選位」端的型別與配對資料。

## 4. 登記與身分驗證（已鎖定）

採「住戶自助 + 登記即註冊」模型，住戶可登入查看自己的登記與抽籤結果。

### 帳號與登入

| 項目 | 決定 |
|---|---|
| 註冊 | **登記即註冊** — 第一次登記就建立「戶」記錄，**不需事先名冊** |
| 帳號主體 | **戶**（以戶號為帳號）；一戶掛 1..N 台車 |
| 登入 | **戶號 ＋ 任一已登記車號**（哪台都行，因車號全域唯一） |
| 登入後 | 看到**整戶**資料（所有車、所有結果），可在登記期內修改 |
| 身分證 | **不收**（與下方個資原則一致）|
| 儲存 | **Supabase（Postgres）+ Edge Functions** — 跨裝置登入看結果；先以 localStorage 介面開發、後換 Supabase（見 §4.1 架構） |
| 防冒名 | 一戶號鎖一次註冊；車號全域唯一不可重複登記；最終由**物業臨櫃查行照＋住戶名冊**把關 |

> **為何不要名冊也行**：登記資料本身即資料庫。代價是有「冒名搶註」風險（搶先用他人戶號登記），但由臨櫃查行照那關擋掉，可接受。物業名冊若日後可得，可加做「登記比對名冊」強化，非必要。

> **為何不用身分證登入**：身分證號為高敏感個資，存於線上系統＝個資法責任；且系統運作不需要它（法律用途在臨櫃簽約手填）。用全域唯一的車號當第二因子即足夠（屬「過濾＋方便」級，非強資安）。

### 4.1 架構：Supabase + Edge Functions（純前端，不自架 server）

部署仍是 **GitHub Pages 純靜態前端**，後端能力由 Supabase 提供，**不另外架/養一台 API server**。

三條方案光譜，**已選 B**：

| 方案 | 後端 | 安全模型 | 維運 | 破壞純靜態部署 |
|---|---|---|---|---|
| A. 純前端直連 Supabase + RLS | 無 | 全靠 RLS policy 寫對 | 幾乎 0 | 否 |
| **B. Supabase + Edge Functions（選定）** | 寄在 Supabase 內 | service_role 藏函式後、RLS 當第二道 | 近 0（CLI 部署） | 否 |
| C. 獨立 API server | 另一台 | 邏輯+密鑰都在 server | 要部署/顧存活/監控 | 是 |

**選 B 的理由**：拿到 C 的安全直覺（密鑰在 server、邏輯藏起來、敏感資料不直接對前端開放），卻幾乎沒有 C 的維運成本——Edge Functions 與 DB 同一專案、`supabase functions deploy` 一行部署、免費額度（50 萬次/月）對「一年一次、約 625 戶」綽綽有餘。C 的「獨立 server」對本專案是不必要的維運債。

### 4.2 安全模型（核心：key 不是密碼，RLS 才是鎖）

> 一句話：**anon key 一定會被 user 從前端拿到，這是設計如此、無法也不需隱藏；資料安不安全完全由 RLS + 「敏感資料只走 Edge Function」決定。**

| Key | 放哪 | 性質 |
|---|---|---|
| **anon key**（publishable）| 前端、可進 repo | 公開沒關係，**只是門牌**，能做什麼受 RLS 管 |
| **service_role key** | 只在 Edge Function 的 secret（`supabase secrets set`）| **繞過 RLS、上帝權限**，外洩=全毀，**絕不進前端、絕不進 git、絕不沾 `VITE_`** |

保護車號/電話的資料流：

```
household / vehicle 表
  ├─ ENABLE ROW LEVEL SECURITY
  └─ 不給 anon 角色任何 SELECT/UPDATE policy   ← anon key 直接查 = 空/403

瀏覽器（持 anon key）── 只能呼叫 ──▶ Edge Function（login / get-my-household / register / update）
                                      ├─ server 端持 service_role（繞過 RLS）
                                      ├─ service_role 永不送進瀏覽器
                                      └─ 比對戶號+車號成功 → 只回「那一戶」資料，絕不整表回傳
```

結論：user 手上的 anon key 對 `vehicle`/`household` **查不到任何一列**；真正能讀的 service_role **從頭到尾沒離開 server**。瀏覽器只能呼叫你寫的函式，函式只吐他自己那戶 → **車號、電話洩不出去**。

### 4.3 三個會害你洩漏的地雷（「資安小心」具體指這個，不是模糊的小心）

1. **🚨 Vite 的坑（本專案最大風險）**：Vite 任何 `VITE_` 開頭的環境變數**會被打包進前端 bundle**。`service_role` key 因此**絕不能取名 `VITE_*`、絕不能出現在 `src/` 任何一行**，只能放 Edge Function 的 secret。寫進前端 = 全社區資料瞬間全裸，最常見死法。
2. **忘記對某張表 `ENABLE RLS`**：漏一張，那張就對 anon key 全開。
3. **policy 寫太鬆**：例如給 anon 一條 `USING (true)` 的 SELECT，等於沒鎖。

### 4.4 上線前驗收測試（必做）

> 開 devtools 複製 anon key → 用它直接 query `vehicle` 表 → **必須回 `[]` 或 401，不能回出任何一筆資料**。回得出資料＝漏了，回不出來＝安全。

每張含個資的表都跑一次這個測試。

### 個資原則（不變）

- **不蒐集、不儲存身分證號**。附件一的身分證號/簽名一律**臨櫃手填**。
- 線上僅處理 戶號＋車號（＋電話）。
- 車牌辨識（若日後做）照片裝置端處理、不上傳。

### 資料模型（初版）

```
household  { 戶號(PK), 電話, createdAt }
vehicle    { 車號(PK, 全域唯一), 戶號(FK), 車種(一般|重機), 第幾輛, 身障, 志願小位 }
           // 預選位(志願) 待大/小型別資料到位後補
```
登入驗證：找 vehicle WHERE 車號=輸入車號 AND 戶號=輸入戶號 → 命中即通過該戶。

### 4.5 實作落點（已鷹架）

| 角色 | 檔案 |
|---|---|
| 前端 facade（async，依 `VITE_SUPABASE_URL` 切後端） | `src/store/db.js` |
| localStorage 後端（離線/測試） | `src/store/local-backend.js`（+ `.test.js`） |
| Supabase 後端（呼叫 Edge Function） | `src/store/supabase-backend.js`、`src/store/supabase-client.js`（只用 anon key） |
| 建表 + RLS deny-all | `supabase/migrations/0001_init.sql` |
| Edge Functions（service_role 在 server） | `supabase/functions/{register,login}/`、`_shared/` |
| 設定步驟 + 洩漏測試 | `supabase/README.md`、`.env.example` |

> 註：`getHousehold(戶號)` 在 Supabase 後端**刻意停用**——以戶號單獨查詢會讓人列舉他戶車號/電話（enumeration 洩漏）。取整戶資料一律走 `login(戶號, 車號)` 雙因子。
